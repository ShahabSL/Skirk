# macOS signing and browser-routing audit — November 15, 2026

This audit separates the two symptoms in [issue #16](https://github.com/ShahabSL/Skirk/issues/16). The reporter's Apple Silicon app was shown as “damaged” after unzipping. Removing the quarantine attribute let it open, but browsing still failed. The current macOS desktop app runs a local SOCKS/HTTP proxy and does not configure Safari or the macOS system proxy automatically. Its main connection panel now says so and gives both local endpoints and a `curl --socks5-hostname` check. A separate live ARM64 GUI run verified the proxy path with exact text, 1 MiB download, and 1 MiB upload responses; it did not validate the reporter's browser settings. Neither issue symptom is closed by that local run.

## Distribution check

The locally built ARM64 `Skirk.app` has a linker-generated ad hoc signature with no sealed resources. `codesign --verify --deep --strict` failed with “code has no resources but signature indicates they must be present”; `spctl --assess --type execute` rejected it. This is the expected state of the `--no-sign` build, not evidence of a corrupt ZIP.

On an isolated copy, the release workflow's order was reproduced with an ad hoc identity: sign the bundled Go sidecar, then sign the app with hardened runtime. Strict deep `codesign` verification passed. The copy was packaged with `ditto -c -k --sequesterRsrc --keepParent`, extracted with `ditto -x -k`, and strict deep verification passed again. Gatekeeper still rejected the copy because an ad hoc identity is not a distribution identity. This check supports the packaging sequence but cannot stand in for a real Developer ID signing and notarization run.

The release workflow already has a conditional Developer ID signing, notarization, stapling, and `spctl` path. It requires all five GitHub Actions secrets: `APPLE_CERTIFICATE` (a base64 `.p12` containing the **Developer ID Application** private key), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_API_KEY`, `APPLE_API_ISSUER`, and `APPLE_API_PRIVATE_KEY`. None of those five names is configured in this repository. The local keychain has valid **Apple Distribution** and **Apple Development** identities, but no **Developer ID Application** identity. Apple says independently distributed notarized software needs Developer ID signing with hardened runtime and a secure timestamp; Apple Distribution is for the Mac App Store. See [Apple's notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) and [distribution signing guidance](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac).

The remaining release prerequisite is an authorized Developer ID Application certificate and private key for the publishing team, plus App Store Connect notary API credentials. Apple's [Developer ID guidance](https://developer.apple.com/developer-id/) says the development team's Account Holder can generate the certificate. Once those are available, the existing signed release job must be run and its notarization, stapled ticket, Gatekeeper assessment, and downloaded ZIP tested on a separate Mac. The current unsigned local build cannot establish those outcomes.

## Browser routing

The native ARM64 test demonstrates an app-managed SOCKS listener and Google Drive transport, not automatic browser routing. A browser that has no proxy configured will continue to use its ordinary network path after Skirk's **Connect** button starts the listeners. The current [desktop setup guide](../../clients/desktop/README.md#macos-proxy-setup) explains HTTP/HTTPS and SOCKS configuration. A Mac system-proxy or packet-tunnel feature would materially simplify this flow, but it is not present in the current bundle; this audit did not change system network settings or add an unverified privileged helper.
