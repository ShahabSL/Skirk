# macOS signing and browser-routing audit — November 15, 2026

This audit separates the two symptoms in [issue #16](https://github.com/ShahabSL/Skirk/issues/16). The reporter's Apple Silicon app was shown as “damaged” after unzipping. Removing the quarantine attribute let it open, but browsing still failed. At the time of the original audit, the macOS desktop app ran a local SOCKS/HTTP proxy and required manual browser setup. A separate live ARM64 GUI run verified the proxy path with exact text, 1 MiB download, and 1 MiB upload responses; it did not validate the reporter's browser settings. A later [macOS system-proxy implementation and native URLSession test](macos-system-proxy-live-2026-11-15.md) address proxy-aware apps in this research branch. The distribution symptom remains open until a signed, notarized package is tested.

## Distribution check

The locally built ARM64 `Skirk.app` has a linker-generated ad hoc signature with no sealed resources. `codesign --verify --deep --strict` failed with “code has no resources but signature indicates they must be present”; `spctl --assess --type execute` rejected it. This is the expected state of the `--no-sign` build, not evidence of a corrupt ZIP.

On an isolated copy, the release workflow's order was reproduced with an ad hoc identity: sign the bundled Go sidecar, then sign the app with hardened runtime. Strict deep `codesign` verification passed. The copy was packaged with `ditto -c -k --sequesterRsrc --keepParent`, extracted with `ditto -x -k`, and strict deep verification passed again. Gatekeeper still rejected the copy because an ad hoc identity is not a distribution identity. This check supports the packaging sequence but cannot stand in for a real Developer ID signing and notarization run.

The release workflow already has a conditional Developer ID signing, notarization, stapling, and `spctl` path. It requires all five GitHub Actions secrets: `APPLE_CERTIFICATE` (a base64 `.p12` containing the **Developer ID Application** private key), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_API_KEY`, `APPLE_API_ISSUER`, and `APPLE_API_PRIVATE_KEY`. None of those five names is configured in this repository. The local keychain has valid **Apple Distribution** and **Apple Development** identities, but no **Developer ID Application** identity. Apple says independently distributed notarized software needs Developer ID signing with hardened runtime and a secure timestamp; Apple Distribution is for the Mac App Store. See [Apple's notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) and [distribution signing guidance](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac).

The remaining release prerequisite is an authorized Developer ID Application certificate and private key for the publishing team, plus App Store Connect notary API credentials. Apple's [Developer ID guidance](https://developer.apple.com/developer-id/) says the development team's Account Holder can generate the certificate. Xcode 27.2 shows **Rookvell LLC, Admin** with a Developer ID Application option in its certificate-creation menu; that menu was inspected read-only, so actual issuance permission was not tested. The browser's Apple Developer and App Store Connect pages both require sign-in, leaving the team's notary API-key access unverified without a login and likely two-factor step. Two local App Store Connect-style `.p8` files could not be tied to the publishing team without reading or using them. Once the team-matched inputs are available, the existing signed release job must be run and its notarization, stapled ticket, Gatekeeper assessment, and downloaded ZIP tested on a separate Mac. The current unsigned local build cannot establish those outcomes.

## Browser routing

The earlier native ARM64 test demonstrated an app-managed SOCKS listener and Google Drive transport, not automatic browser routing. The new optional **System proxy** mode configures HTTP/HTTPS for proxy-aware apps on the active macOS network service and restores the saved settings on disconnect. Its bounded native URLSession test carried exact text and 1 MiB GET/POST traffic through Drive; the [desktop setup guide](../../clients/desktop/README.md#macos-proxy-setup) explains both automatic and manual modes. Safari and Chrome were not separately tested, apps that ignore system proxy settings remain outside this mode, and no macOS packet-tunnel VPN was added.
