# Live Drive push-notification probe

Run on 2026-11-15 CST with only the isolated `shahabpre@gmail.com` personal-test exit kit and the `google_front_pinned` route. Each arm used a fresh, temporary `workers.dev` HTTPS receiver with an isolated D1 event log. The Worker stamped notification arrival before writing the event to D1. Eight `/time` exchanges calibrated Worker versus Mac clocks; the best round-trip bounds were ±9.91 ms for `changes.watch` and ±11.34 ms for `files.watch`. Receiver polling latency did not enter the push timing. Raw reports and channel tokens stayed in ignored `.skirk-runs` paths.

The two arms used one generated-ID metadata slot under the test mailbox, a five-minute channel expiration, six sequential description PATCHes, one immediate known-ID GET after each PATCH, a 10-second per-PATCH notification deadline, and a 4,000 estimated Drive-unit limit. The change-feed arm created its object *after* opening `changes.watch`; the per-file arm created and read its object *before* opening `files.watch`. Both used Google Drive's approved `drive.file` scope. The change-feed arm obtained a page token via `changes.getStartPageToken` and confirmed the new object through `changes.list` after its create notification.

The `changes.watch` create notification arrived **3,685.6 ms from the create request start**; the create request itself took 471.1 ms. One subsequent `changes.list` call identified the new object in 144.8 ms. Five PATCH notifications were observed in the per-PATCH window. The Worker recorded another change event later, after the sixth window had expired and cleanup began. The empty notification body does not identify which file changed, so that late event cannot be attributed unambiguously to the sixth PATCH or cleanup.

The per-file receiver delivered six `update` events. Its 2.53-second median was faster than the change-feed receiver's 5.45-second observed median, but **13.4 times** the immediate known-ID GET median in this small run. The change-feed comparison was **34.4 times** the GET median for its five observed notifications. These ratios compare delays after a successful PATCH response, not end-to-end application latency. Six samples per arm and one location cannot establish tail percentiles, capacity, or a universal lower bound for Google notification delivery.

Neither push channel is suitable as Skirk's interactive default on this evidence. `files.watch` targets a known file and cannot discover an unknown new mailbox object. `changes.watch` can signal a new object but its notifications contain headers only; a `changes.list` call is still required to identify it. Both require a public HTTPS callback and therefore do not replace Drive polling for a client whose region can only reach Google through the configured Google front. An exit with a reachable callback could use push as an *optional idle wakeup* to save polling quota; active known-ID polling still provided much lower measured latency here. A channel also needs explicit replacement before expiration: Drive caps `files.watch` at one day and `changes.watch` at one week, with no automatic renewal.

Both channel stop calls returned **204**. Each generated object was deleted, returned **404 twice** on exact-ID checks, and produced zero matches in an immediate and a 30-second delayed unique-prefix sweep. Both temporary Workers and D1 databases were deleted; each callback returned **404** afterward. No channel, test file, Worker, or D1 database was left active. The private reports are `.skirk-runs/drive-changes-watch-live.json` and `.skirk-runs/drive-files-watch-live.json` in the isolated worktree.
